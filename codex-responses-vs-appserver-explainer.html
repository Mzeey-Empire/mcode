mcode · codex integration · design spec

Two ways to drive Codex — and the one you already shipped

You asked whether mcode should adopt Hermes Agent's codex_responses transport because it sounded "more efficient." I read both codebases. The honest answer up front: mcode already implements the app-server path, and for a desktop orchestrator it is the right one. Hermes' efficiency trick is real — but it solves a problem mcode doesn't have, and adopting it would mean throwing away your native event stream. This document explains both flows from zero, the trade-offs, and the small set of Hermes ideas actually worth porting.

Your path: codex app-server (JSON-RPC) Hermes' default: codex_responses (HTTPS) Verdict: keep app-server, port 3 ideas

01

What mcode already does

Before specing anything new, you should know exactly what you have — because the premise of "let's copy Hermes" partly dissolves on contact with your own tree. mcode's Codex provider is already a persistent codex app-server integration, and it's more mature than Hermes' equivalent in several places.

The evidence, from your own code:

  • packages/providers/src/private/codex/codex-app-server.ts — a persistent child-process manager that spawns codex app-server and completes the full JSON-RPC handshake: initialize → initialized → thread/resume or thread/start.
  • codex-provider.ts:2 — "Codex provider adapter using the persistent codex app-server subprocess. Each session owns one CodexAppServer process that stays alive between turns."
  • codex-app-server.ts:598 — you already opt into capabilities: { experimentalApi: true }, the same flag Hermes uses.
  • codex-event-mapper.ts — translates raw JSON-RPC notifications into provider-neutral AgentEvents, exactly the projection Hermes does in codex_event_projector.py.
  • You've already solved problems Hermes only partially handles: a liveness watchdog (TURN_TIMEOUT_MS with an RPC ping), Windows JobObject / taskkill cleanup, warm-up of a throwaway app-server to cut cold-start latency, and native sub-agent / collaboration threads.
The reframe

You are not missing the app-server implementation — you wrote it. So this document is not "how to build what Hermes built." It's "here is the other architecture Hermes defaults to, why it's efficient, whether it beats what you have, and what (if anything) to steal."

02

The two paths, side by side

"Codex" is not one thing you talk to. There are two front doors, and they lead to different rooms. Everything in this document hangs on understanding the difference.

Path A · the app-server

codex app-server · JSON-RPC 2.0 over stdio · what mcode uses
  • You launch the Codex CLI itself as a subprocess.
  • That subprocess runs its own agent loop: it decides when to call tools, run shell commands, read files.
  • You send it turns (turn/start) and it pushes events back (item/* notifications).
  • It owns the thread, the tools, and the compaction.

Path B · the Responses API

POST /backend-api/codex/responses · HTTPS · Hermes' default
  • You call OpenAI's Responses HTTP endpoint directly, like any LLM API.
  • Your code runs the agent loop: you get a tool call, you execute it, you send the result back.
  • There is no subprocess and no built-in coding tools.
  • You own the loop, the tools, the transcript, and the caching.
One sentence to hold onto

Path A rents Codex's brain and its hands. Path B rents only the brain — you bring your own hands. Hermes is a general agent that already had hands (its own tools), so it chose B. mcode is an orchestrator whose whole job is to supervise Codex's hands, so it chose A.

03

Flow A — the app-server, as if you've never seen it

This is the flow mcode runs today. I'll walk it slowly, because understanding it is what lets you judge whether the alternative is worth anything.

Fig 1 — One persistent subprocess per session. mcode sends turns; Codex does the agentic work and streams events back.

  1. Spawn the subprocess once per session

    mcode runs codex app-server as a long-lived child (codex-app-server.ts:1008). It stays alive between turns — this is the hard-won lesson in your provider-architecture.md: per-turn spawning caused Windows stdin races and abort-signal bugs, so you moved to persistent processes.

  2. Handshake

    You send initialize with { capabilities: { experimentalApi: true } }, then an initialized notification. The experimental flag unlocks the v2 protocol surface (approvals reviewer, richer item lifecycle) that you already use.

  3. Start (or resume) a thread

    thread/start carries the model, working directory, sandbox mode, and approval policy. On reconnect you call thread/resume to reattach to an existing rollout — Hermes' app-server path can't do this cleanly, but yours can.

  4. Send a turn

    turn/start hands Codex the user's message. From here Codex drives: it decides to run a shell command, asks for approval, edits a file. mcode's job is to supervise, not to execute.

  5. Stream events back

    The app-server pushes item/* notifications — agent messages, command executions, file changes, reasoning. Your CodexEventMapper projects these into provider-neutral AgentEvents that flow to the renderer over WebSocket. This is the live-streaming UX that is mcode's reason to exist.

  6. Turn completes; process stays warm

    turn/completed ends the turn, but the subprocess lives on for the next one. A watchdog pings it if a turn goes silent for 5 minutes, so a wedged Codex doesn't leave your UI stuck on "thinking."

Why this fits mcode

mcode is an orchestrator: its value is running many supervised sessions across git worktrees, streaming what each agent does, and enforcing approvals. The app-server gives you a faithful, granular, real-time view of Codex's own loop — which is exactly the thing you're orchestrating.

04

Flow B — the Responses API, Hermes' way

Now the alternative. Hermes' default (codex_responses) ignores the app-server entirely and treats Codex as a plain LLM endpoint. The crucial difference: the agent loop moves into your process.

Fig 2 — No subprocess. Each tool call is a round-trip: the API proposes, your code disposes. The loop is yours.

  1. No subprocess — just an HTTPS call

    You POST to chatgpt.com/backend-api/codex/responses. There's no codex app-server, no JSON-RPC, no child to babysit. The request carries your messages, your tool schemas, and — critically — a prompt_cache_key.

  2. The model replies with a tool call, not an action

    The API doesn't run anything. It returns "I want to call run_shell with these args." Execution is your problem.

  3. Your code executes the tool

    Hermes runs the shell command / file edit in its own process, using its own tools. This is the whole point: Hermes already had a rich toolset, so it didn't need Codex's.

  4. Send the result back, repeat

    You append the tool result to the conversation and POST again. This loop — propose, execute, feed back — repeats until the model returns a plain message instead of a tool call.

  5. You own the transcript and the caching

    Because you see every message, you can persist the thread locally, replay encrypted reasoning blobs, and — the efficiency trick — keep the prompt prefix identical so the server's cache keeps hitting.

What you'd have to build

To use this path, mcode would need to reimplement the agent loop and every coding tool itself — shell execution, file editing, sandboxing, approvals — and then project that self-run loop back into your event stream. You'd be rebuilding the thing Codex already does, just to get at the caching.

05

Why Hermes' path is "efficient" — the four levers

The efficiency you heard about is real, but it's specific. It comes from four mechanisms that are only possible when you control the wire (Path B). Here's each, with the actual code that does it.

1 · Prompt caching, engineered for hits ← the big one

Every agent turn resends the system prompt, tool schemas, and history. On a naive setup that's all re-processed (and re-billed) each time. Hermes makes the shared prefix cacheable by deriving a content-addressed prompt_cache_key: 

# hermes-agent/agent/transports/codex.py
content = f"{scope_id}\x00{instructions}\x00{tools_part}"
return "pck_" + sha256(content).hexdigest()[:24]
# → identical static prefix = same key = server cache hit
# comments cite 93–99% measured hit rate vs 0% on chat/completions

And it defends that key against the things that would normally bust the cache:

  • Compression / session rotation — the key derives from a rotation-stable cache_scope_id, not the physical session id, so compacting the context doesn't cold-start the cache.
  • Cron jobs — per-fire timestamps are stripped so every run of one job shares a cache scope.
  • Long contexts — prompt_cache_retention: "24h" extends the cache window on supported models.

2 · store: false + local encrypted-reasoning replay

Hermes tells OpenAI not to retain the conversation (store: false). Instead it captures the model's encrypted reasoning blobs each turn, stores them in its local SQLite (~/.hermes/state.db), and replays them on the next request. The model keeps cross-turn coherence without OpenAI holding any state — and without Hermes re-summarizing. 

# request:  codex_responses_adapter.py:803
{ "model": …, "input": …, "store": false }
# response carries item.encrypted_content → persisted locally →
# replayed next turn as opaque blobs (sealed to the issuer)

3 · Native server-side compaction

When context fills, Hermes can hand compaction to the API itself via context_management. The server returns an encrypted compaction checkpoint that Hermes persists and replays — replacing the "summarize the whole history with a second LLM call" approach with one server-side operation.

4 · Subscription billing, not metered API

The route rides ChatGPT-subscription OAuth (hermes_cli/auth_codex.py), so usage draws down a plan's included quota rather than per-token pricing. Combined with a high cache-hit rate, the marginal cost per turn drops sharply.

The catch that matters for you

Levers 1–3 require owning the request. In the app-server path, the Codex CLI builds the request — mcode can't set prompt_cache_key, can't set store, can't replay reasoning. You'd only get these by moving to Path B and reimplementing the loop. Lever 4 (subscription auth) you can get without changing architecture — see §8.

06

The trade-offs, honestly

Here's the full ledger. The "winner" column is from mcode's perspective as a desktop orchestrator, not in the abstract.

ConcernPath A · app-server (yours)Path B · Responses (Hermes)Better for mcode
Agent loop Codex CLI runs it natively You must reimplement it + all tools A
Live event stream Rich native item/* events (commands, file changes, reasoning) You only see your own loop's steps A
Prompt caching control None — Codex builds the request Full (prompt_cache_key, retention) B
Thread resume / fork thread/resume, native sub-agent threads Manual; you rebuild state A
Approvals & sandbox Codex's native permission profiles You enforce your own A
Compaction Codex-native, automatic Server-side via context_management (you wire it) A
Process to babysit Yes — watchdog, JobObject, taskkill No — stateless HTTPS B
Subscription auth Codex CLI's own session Your own OAuth store, full control Tie
Multi-provider symmetry Codex-specific protocol Same shape as other HTTPS providers B
Effort to adopt Already shipped Large — new loop, tools, projection A
The pattern

Path B wins on wire-level economics (caching, no subprocess, provider symmetry). Path A wins on everything an orchestrator is for (native loop, event fidelity, resume, approvals). mcode's product is the second column. The efficiency levers don't move that.

07

Recommendation for mcode

Verdict

Keep the app-server path. Do not reimplement Hermes' codex_responses transport. The efficiency you heard about is real but belongs to a different product shape — a general agent that already owns its tools and wants to minimize token cost. mcode is a supervised-session orchestrator; its value is the native event stream and lifecycle control that only the app-server provides. Rebuilding the loop to chase cache hits would cost you the thing that makes mcode useful, for savings that largely evaporate once you're re-executing tools yourself.

That said, three Hermes ideas are genuinely worth porting, because they don't require changing your architecture. That's the next section.

08

What to actually port — three surgical ideas

Each of these stands alone, fits your existing app-server design, and has a clear place to live in your tree.

1 · Subscription-OAuth usage & quota introspection (highest value, no arch change)

Hermes calls the ChatGPT /wham/usage endpoints to show remaining plan quota and surface rate-limit windows. You already receive mapCodexRateLimitsToUsage from the app-server — but Hermes goes further with a dedicated account-usage reader and a local OAuth token store kept separate from the Codex CLI's (~/.hermes/auth.json vs ~/.codex/) so one app's token rotation can't invalidate the other.

  • Where it lives: a new module beside codex-provider.ts, e.g. codex-usage.ts, feeding your existing ProviderUsageInfo.
  • Why: richer "time to reset / plan remaining" UI than the app-server's rate-limit push alone gives you.

2 · Cache-scope discipline (concept, applies to your HTTPS providers)

You can't set prompt_cache_key on the app-server — but the idea transfers to any provider where mcode does build the request (and to a future direct-Responses provider if you ever add one). The lesson: derive cache identity from stable content + a rotation-stable scope, never from a per-session or per-fire id.

  • Where it lives: a small cache-scope.ts util in packages/shared — the SHA-256-of-(scope, instructions, sorted-tools) pattern, plus the cron-timestamp-stripping normalization.
  • Why: it's cheap, correct, and reusable the moment you add a provider whose wire you control.

3 · Content-free local transcript sidecar (hygiene)

Hermes persists reasoning/compaction blobs to local SQLite as a sidecar on the assistant message (codex_reasoning_items), kept out of the user-facing transcript. You already have a clean event boundary (ProviderRuntimeEvent vs renderer-bound AgentEvent); adopting the "provider-native evidence travels only in the extension, never to the renderer" discipline for any future replay state keeps your projection honest.

  • Where it lives: you already enforce this in contracts — this is a validation of your existing rule, not new work.
Explicitly not recommended

Do not port store:false reasoning replay or context_management compaction into the app-server path. They only function when you own the request. Bolting them onto a subprocess you don't control adds complexity for zero effect.

09

Glossary — the terms, plainly

TermWhat it actually means
Agent loopThe cycle of model proposes a tool call → something executes it → result goes back to the model, repeated until the model just answers. In Path A the Codex CLI runs it; in Path B your code does.
app-serverA mode of the Codex CLI (codex app-server) that runs as a persistent subprocess and speaks JSON-RPC over stdio, so another program can drive it.
JSON-RPC 2.0A simple request/response messaging format. mcode sends {"method":"turn/start",…}; Codex replies and pushes notifications back. NDJSON = one JSON object per line.
Responses APIOpenAI's HTTPS endpoint (/responses) for chat-with-tools. Stateless by default — you send the whole conversation each call.
Prompt cachingThe server remembers the unchanged prefix of your prompt so repeat turns are faster and cheaper. Needs a stable prompt_cache_key to hit.
prompt_cache_keyA label you attach so the server can route your request to its cached prefix. Same key + same prefix = cache hit.
store:falseTells OpenAI not to keep your conversation server-side. You keep state locally and resend what you need.
Encrypted reasoningThe model's hidden chain-of-thought, returned as an opaque blob only OpenAI can read. Replaying it next turn preserves coherence without you seeing or re-summarizing it.
CompactionShrinking a long conversation so it fits the context window — either by summarizing (your code) or natively (the server / Codex does it).
Thread / turnA thread is one Codex conversation; a turn is one user-message-to-final-answer exchange inside it.
WorktreeA separate git working copy. mcode gives each thread its own so parallel agents don't collide.
ProviderRuntimeEvent vs AgentEventmcode's boundary: the raw provider event (may carry native evidence) vs the cleaned, provider-neutral event that's safe to show the renderer.
